# Monorepo Template

Шаблон монорепозиторію з готовою CI/CD-інфраструктурою. Підтримує одночасно кілька мов і технологій — Node.js, Python, Go, Rust, Java, Docker, Terraform — без ручного налаштування пайплайнів.

---

## Філософія структури

Монорепо — це єдиний Git-репозиторій, який містить кілька незалежних проєктів: застосунки, сервіси, бібліотеки та інфраструктуру. На відміну від підходу "один проєкт — один репо" (polyrepo), монорепо дає:

- **Єдину точку правди** — всі зміни, залежності та версії видно в одному місці.
- **Атомарні зміни** — один PR може одночасно змінити бібліотеку і всі сервіси, що її використовують, без синхронізації між репозиторіями.
- **Спільне CI/CD** — не треба дублювати пайплайни для кожного сервісу окремо.
- **Простішу навігацію** — новий член команди одним `git clone` отримує весь проєкт.

Структура репозиторію розділена за **типом артефакту**, а не за командою чи доменом. Це принципово: `apps/` і `services/` — різні речі не тому, що так прийнято, а тому що вони мають різний lifecycle та різне призначення.

---

## Структура

```
.
├── apps/               # Кінцеві застосунки — те, з чим взаємодіє кінцевий користувач
├── services/           # Бекенд-сервіси — внутрішня логіка, API, воркери
├── libs/               # Спільні бібліотеки з бізнес-логікою
├── packages/           # Спільні технічні пакети (конфіги, типи, утиліти)
├── infra/              # Інфраструктурний код (Terraform, Helm, Docker Compose)
├── .github/
│   └── workflows/
│       └── ci.yml      # Єдиний CI/CD пайплайн для всього репо
├── .gitignore
└── README.md
```

## Детальна логіка директорій

### `apps/` — Застосунки

Тут живуть **кінцеві продукти**, які безпосередньо бачить або використовує користувач. Кожен підкаталог — окремий застосунок зі своїм стеком і власними залежностями.

```
apps/
├── web/          # Основний веб-інтерфейс (React, Next.js тощо)
├── admin/        # Адмін-панель
└── mobile/       # Мобільний застосунок (React Native, Flutter)
```

**Ключові ознаки `apps/`:**
- Має власний `package.json`, `pyproject.toml` або аналог — тобто є точкою входу зі своїми залежностями.
- Залежить від `libs/` і `packages/`, але **ніколи не імпортується** іншими застосунками чи сервісами.
- Деплоїться як повноцінний артефакт: Docker-образ, статичний бандл, APK тощо.
- Відповідає за UI/UX та взаємодію з кінцевим користувачем; бізнес-логіку делегує сервісам через API.

**Коли щось іде в `apps/`, а не в `services/`:** якщо це має інтерфейс і взаємодіє з людиною — це `apps/`. Якщо це HTTP API, черга задач або воркер без UI — це `services/`.

---

### `services/` — Бекенд-сервіси

Тут живе **серверна логіка**: API-сервери, фонові воркери, обробники черг, мікросервіси. Кожен підкаталог — незалежний процес, який деплоїться і масштабується окремо.

```
services/
├── auth/         # Сервіс авторизації та автентифікації
├── api/          # Основний API-гейтвей
├── scanner/      # Воркер, що виконує фонові задачі
└── notifier/     # Сервіс відправки нотифікацій
```

**Ключові ознаки `services/`:**
- Кожен сервіс — **незалежна одиниця деплою**. Можна оновити `auth/` без перезапуску `scanner/`.
- Має власний `Dockerfile` та, як правило, власний запис у `docker-compose.yml` або Helm-чарті.
- Спілкується з іншими сервісами через чітко визначені інтерфейси: REST API, gRPC, черги повідомлень (Kafka, RabbitMQ, Redis Streams).
- Не ділиться спільним станом через пам'ять — тільки через зовнішні сховища (БД, кеш).
- Може бути написаний на будь-якій мові — CI підхопить автоматично.

**Чому не класти всю логіку в один сервіс:** великий монолітний сервіс важко масштабувати точково. Якщо `scanner/` навантажений — можна підняти тільки його репліки, не чіпаючи `auth/`.

---

### `libs/` — Спільні бібліотеки

Тут живе **бізнес-логіка, яка потрібна більш ніж одному сервісу або застосунку**. Бібліотека — це не самостійний процес, вона завжди є залежністю чогось іншого.

```
libs/
├── core/         # Базові доменні сутності та бізнес-правила
├── auth-client/  # Клієнт для взаємодії з сервісом авторизації
└── db/           # Спільні моделі та ORM-конфіги
```

**Ключові ознаки `libs/`:**
- **Не деплоїться** самостійно — тільки збирається разом з тим, хто її використовує.
- Містить логіку, специфічну для домену проєкту (на відміну від `packages/`, де технічні утиліти).
- Зміна в `libs/core/` потенційно зачіпає всіх споживачів — тому CI перевіряє це автоматично.
- Версіонується разом з репо (немає окремих npm-версій всередині монорепо).

**Головне правило `libs/`:** якщо одну й ту саму логіку треба написати в двох різних сервісах — вона йде в `libs/`. Дублювання коду між сервісами є антипатерном.

---

### `packages/` — Технічні пакети

Схоже на `libs/`, але для **технічних**, а не бізнесових речей. Тут живуть конфіги, типи, утиліти, які не несуть доменної специфіки.

```
packages/
├── config/       # Спільні конфіги (ESLint, Prettier, tsconfig)
├── types/        # Shared TypeScript типи та інтерфейси
├── utils/        # Технічні утиліти (форматування дат, парсинг тощо)
└── ui/           # Спільні UI-компоненти (Design System)
```

**Різниця між `libs/` і `packages/`:**

| | `libs/` | `packages/` |
|---|---|---|
| Тип логіки | Бізнесова (домен-специфічна) | Технічна (загальна) |
| Приклад | `libs/auth-client` | `packages/utils` |
| Залежить від домену? | Так | Ні |
| Можна перенести в інший проєкт? | Ні | Так |

Ця межа умовна і залежить від команди, але чітке розділення спрощує розуміння — де шукати бізнес-логіку, а де інфраструктурний код.

---

### `infra/` — Інфраструктура як код

Тут живе **все, що стосується деплою та оточення**: Terraform-модулі, Helm-чарти, Docker Compose файли, конфіги Kubernetes.

```
infra/
├── terraform/         # Terraform-модулі (хмарні ресурси: VPC, БД, S3)
│   ├── modules/       # Перевикористовувані модулі
│   └── environments/  # Конфіги для dev / staging / prod
├── helm/              # Helm-чарти для Kubernetes
│   └── my-service/
├── docker-compose.yml # Локальне оточення для розробки
└── k8s/               # Raw Kubernetes маніфести (якщо без Helm)
```

**Ключові ознаки `infra/`:**
- Інфраструктурний код версіонується **разом з кодом застосунків** — це дозволяє зрозуміти, яка інфра відповідала якій версії сервісу.
- `docker-compose.yml` в `infra/` — це **локальне оточення для розробників**: запускає всі сервіси, БД, кеш одною командою.
- Terraform `environments/` містить окремі змінні для кожного оточення — ніколи не хардкодиться prod-конфіг у `dev`.
- Зміни в `infra/` проходять окремий CI-крок (`terraform-ci`): перевірка форматування, ініціалізація і валідація.

**Чому інфра в монорепо, а не окремо:** зміна API сервісу і відповідна зміна в Helm-чарті (нові env-змінні, порти) йдуть одним PR. Немає ризику що код задеплоїться з застарілою конфігурацією.

## CI/CD пайплайн

Пайплайн (`.github/workflows/ci.yml`) складається з чотирьох стадій, які виконуються послідовно.

```
┌─────────────┐
│   analyze   │  Визначає, які мови присутні в репо
└──────┬──────┘
       │
┌──────▼──────┐
│  security   │  Завжди сканує на секрети та вразливості
└──────┬──────┘
       │
┌──────▼──────────────────────────────────────────────────┐
│  node-ci │ python-ci │ go-ci │ rust-ci │ java-ci │ ...  │  Паралельно
└──────────────────────────────────┬──────────────────────┘
                                   │
                          ┌────────▼────────┐
                          │   ci-status     │  Агрегація результатів
                          └─────────────────┘
```

### Стадія 1 — Аналіз (`analyze`)

Перший крок — **детекція**: пайплайн не знає заздалегідь, що є в репо, і з'ясовує це динамічно. Перевіряється наявність файлів-маркерів:

| Файл-маркер | Технологія | Job, що запускається |
|---|---|---|
| `package.json` | Node.js | `node-ci` |
| `pyproject.toml` / `requirements*.txt` | Python | `python-ci` |
| `go.mod` | Go | `go-ci` |
| `Cargo.toml` | Rust | `rust-ci` |
| `pom.xml` / `build.gradle` / `build.gradle.kts` | Java | `java-ci` |
| `Dockerfile*` / `docker-compose.yml` | Docker | `docker-ci` |
| `*.tf` | Terraform | `terraform-ci` |

Результати зберігаються як `outputs` і передаються в наступні jobs через `needs.analyze.outputs.*`. Якщо маркер не знайдено — відповідний job пропускається через умову `if: needs.analyze.outputs.has_X == 'true'`.

Це дозволяє **додавати нові мови в репо без жодних змін у пайплайні** — достатньо з'явитися файлу `go.mod`, і `go-ci` запуститься автоматично.

### Стадія 2 — Безпека (`security`)

Запускається **завжди**, незалежно від мови. Два інструменти з різною поведінкою при помилках:

**Gitleaks** — шукає секрети в коді та git-історії: API-ключі, паролі, токени, приватні ключі. Налаштований з `continue-on-error: true` — знайдені проблеми видно у логах, але не блокують пайплайн повністю. Свідома компромісна позиція: краще бачити попередження, ніж повністю зупиняти роботу команди.

**Trivy** — сканує файлову систему репозиторію на відомі CVE-вразливості в залежностях та базових образах. Налаштований на `exit-code: 1` при знахідках `CRITICAL` або `HIGH` — це **блокуючий крок**. Якщо Trivy знайшов критичну вразливість, пайплайн зупиняється і merge заблокований.

### Стадія 3 — Мовні перевірки

Всі jobs цієї стадії виконуються **паралельно** (якщо detected). Кожен дотримується одного принципу: встановити → перевірити стиль → тести → зібрати.

| Job | Деталі |
|---|---|
| `node-ci` | `npm ci` (детермінована установка з lockfile) → lint → test → build |
| `python-ci` | pip install → flake8 (статичний аналіз) → pytest |
| `go-ci` | `go mod download` → `go vet` (статичний аналіз) → `go test -v` → `go build` |
| `rust-ci` | `cargo fmt --check` → `cargo clippy -D warnings` (попередження = помилки) → test → release build |
| `java-ci` | Автовизначає Gradle або Maven за наявністю файлів, запускає відповідні тести |
| `docker-ci` | Знаходить всі `Dockerfile*` до глибини 2 рівнів, будує кожен через `buildx` з кешуванням GHA |
| `terraform-ci` | `fmt -check` → `init -backend=false` (без реального стейту) → `validate` |

Кешування увімкнено для всіх jobs через відповідні екшени (`cache: 'npm'`, `cache: true` для Go тощо) — повторні запуски значно швидші.

### Стадія 4 — Фінальний статус (`ci-status`)

Останній job завжди виконується (`if: always()`) і агрегує результати всіх попередніх. Якщо хоча б один job завершився з `failure` або `cancelled` — `ci-status` завершується з кодом 1 і весь пайплайн вважається провальним.

Цей job виступає **єдиною required status check** для захисту `main`-гілки. Замість того щоб перераховувати всі 8 jobs у branch protection rules, достатньо вказати один `ci-status`.

## Concurrency

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

Якщо запушити два коміти підряд в одну гілку, другий run автоматично скасує перший. Це запобігає черзі запусків і економить хвилини GitHub Actions — особливо актуально для feature-гілок з частими комітами.

## Необхідні дозволи

| Право | Для чого |
|---|---|
| `contents: read` | Читання коду репозиторію |
| `pull-requests: write` | Публікація коментарів до PR |
| `security-events: write` | Завантаження SARIF-звітів у Security → Code Scanning tab GitHub |

## Як додати новий сервіс

1. Створити директорію в `services/`:
   ```
   services/my-service/
   ├── main.py          # або main.go, main.rs тощо
   ├── Dockerfile
   └── pyproject.toml   # або go.mod, Cargo.toml
   ```
2. CI підхопить нову мову автоматично через детекцію файлів-маркерів.
3. Якщо сервіс потребує хмарних ресурсів — додати Terraform-модуль в `infra/terraform/`.
4. Для локальної розробки — додати сервіс в `infra/docker-compose.yml`.

## Як додати спільну бібліотеку

1. Визначити тип: бізнес-логіка → `libs/`, технічна утиліта → `packages/`.
2. Створити підкаталог з відповідним маніфестом залежностей.
3. Імпортувати в `apps/` або `services/` через відносний шлях або workspace-посилання (залежить від мови).
